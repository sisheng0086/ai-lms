Compilation Model & Process Memory Layout

C++ Build Pipeline (Source to Binary) Toolchain

The translation from human-readable code to an executable passes through four strictly sequenced phases:

[Source .cpp / .h] │ (1) Preprocessor (g++ -E): Expands #include, #define macros, #ifdef ▼ [Translation Unit (.i)] │ (2) Compiler (g++ -S): Lexing, parsing, AST, optimization -> Assembly ▼ [Assembly (.s)] │ (3) Assembler (as / g++ -c): Translates assembly to machine code ▼ [Object File (.o / .obj)] │ (4) Linker (ld / g++): Resolves external symbols, imports static/dynamic ▼ libraries, fixes addresses -> Single Executable / Binary [Executable Binary (.exe / elf)]
Key Rule: Header files (.h/.hpp) should contain declarations, inline functions, and template definitions. Avoid defining non-inline functions in headers to prevent One Definition Rule (ODR) violation errors during linking.
Virtual Address Space Memory Layout Architecture

Every standard OS process executes within an isolated virtual memory space:

High Memory 0xFFFFFFFF ┌────────────────────────────────────────┐ │ Kernel Space (OS reserved) │ ├────────────────────────────────────────┤ │ STACK (Grows Downward ▼) │ -> Local vars, call frames, return IPs │ │ │ Fastest, automated allocation/free │ ▼ │ │ [ Free Unallocated Memory ] │ │ ▲ │ │ │ │ │ HEAP (Grows Upward ▲) │ -> Dynamic alloc (new, malloc), manual ├────────────────────────────────────────┤ lifetime, fragmented if unmanaged │ BSS Segment │ -> Uninitialized global & static vars (0) ├────────────────────────────────────────┤ │ Data Segment │ -> Initialized global & static vars ├────────────────────────────────────────┤ │ Text Segment (Code Segment) │ -> Read-only machine bytecode, string lits └────────────────────────────────────────┘ Low Memory 0x00000000
  • Stack Allocation: Instantaneous ($O(1)$) pointer bump, automatically rewound on scope exit. Fixed size (typically 1–8 MB). Overflow causes Stack Overflow.
  • Heap Allocation: Slower ($O(1)$ to $O(n)$) free-list lookup, managed via OS syscalls (brk / mmap). Flexible size, potential memory leaks.

Read pointers right-to-left to decode const qualifiers:

const int* p1 = &a;       // Data is const

p1 = &b;                  // OK: can reassign pointer

int* const p2 = &a;       // Pointer is const
*p2 = 10;                 // OK: modify data

Object-Oriented Programming (OOP) & Resource Lifecycle

Class Architecture & The Big Five (Rule of 5 / Rule of 0) Crucial

If a class manages an explicit raw resource (heap memory, socket, file descriptor), you must define or delete all five special member functions:

class Buffer {
private:
    size_t m_size;
    int*   m_data;
public:
    // 1. Constructor
    Buffer(size_t sz) : m_size(sz), m_data(new int[sz]{}) {}

    // 2. Destructor
    ~Buffer() { delete[] m_data; }

    // 3. Copy Constructor (Deep Copy)
    Buffer(const Buffer& o) : m_size(o.m_size), m_data(new int[o.m_size]) {
        std::copy(o.m_data, o.m_data + m_size, m_data);
    }

    // 4. Copy Assignment Operator (Copy-and-Swap idiom)
    Buffer& operator=(Buffer o) {
        swap(*this, o);
        return *this;
    }

    // 5. Move Constructor (Resource Transfer - no allocation!)
    Buffer(Buffer&& o) noexcept : m_size(o.m_size), m_data(o.m_data) {
        o.m_data = nullptr;  // Neutralize zombie source
        o.m_size = 0;
    }
};
Value Categories & Move Semantics C++11

Understanding lvalues and rvalues is the key to zero-copy performance:

  • lvalue (Left Value): Has an identifiable identity / memory address (e.g. named variables x, str, *ptr). Can take its address &x.
  • rvalue (Right Value): Temporary object, expression result, or literal that has no persistent address (e.g. 42, x + y, temporary returned objects).
  • Rvalue Reference (T&&): Binds to temporaries, enabling stealing resources instead of deep-copying.
  • std::move(x): Casts an lvalue unconditionally to an rvalue reference (static_cast<T&&>(x)). Does NOT move anything itself; it simply signals that x can be pilfered!
Rule of Zero: Prefer designing classes that rely exclusively on standard components (std::vector, std::string, std::unique_ptr). They handle all 5 operations automatically with zero manual bugs!

Polymorphism, Virtual Tables & Object Layout

Static vs Dynamic Polymorphism Theory

StaticTemplates, Function OverloadingCompile-timeZero runtime overhead, larger binary (code bloat)

class Shape {
public:
    virtual void draw() const = 0; // Pure virtual -> Abstract class
    virtual ~Shape() = default;     // ALWAYS virtual destructor!
};
class Circle : public Shape {
public:
    void draw() const override { std::cout << "Circle"; }
};
Mandatory Virtual Destructor: If deleting a derived object via a base pointer (Shape* s = new Circle(); delete s;), the base destructor MUST be virtual. Otherwise, only the base destructor runs, causing UB and memory leaks!

How dynamic dispatch works under the hood at machine level:

Instance in Memory: Circle Object ┌─────────────────────────────────┐ │ __vptr (8 bytes pointer) │───┐ ├─────────────────────────────────┤ │ │ m_radius (8 bytes double) │ │ └─────────────────────────────────┘ │ ▼ Virtual Method Table (vtable) [Read-Only Data Segment] ┌──────────────────────────────────────────────────┐ │ [0]: &Circle::~Circle() (Destructor address) │ ├──────────────────────────────────────────────────┤ │ [1]: &Circle::draw() (Overridden draw) │ ├──────────────────────────────────────────────────┤ │ [2]: &Shape::area() (Inherited base func) │ └──────────────────────────────────────────────────┘ Invocation: ptr->draw() ==> (*(ptr->__vptr[1]))(ptr);

RAII & Smart Pointer Architecture

std::unique_ptr Sole Ownership

Zero-cost abstraction. Unique, non-copyable ownership. Automatically deletes object when falling out of scope.

// Construction (C++14):
auto p = std::make_unique<Widget>(10);

// Cannot copy!
// auto p2 = p; // Compile Error!

// Ownership transfer:
auto p2 = std::move(p); // p is now null
p2->execute();

Cost: Exactly identical to raw pointer in size and runtime efficiency!

std::shared_ptr Shared Reference Counting

Multiple owners manage single heap object via a heap-allocated Control Block.

auto s1 = std::make_shared<Node>(42);
auto s2 = s1; // Ref count = 2
// Object freed when last shared_ptr dies
shared_ptr s1 ──┐ shared_ptr s2 ──┴─► [Control Block] - Strong Count: 2 - Weak Count: 0 - Managed Object ptr

Always use make_shared to allocate object & control block in one contiguous chunk.

std::weak_ptr Breaking Cycles

Non-owning observer. Does not increment strong reference count. Used to break circular dependencies.

class Node {
public:
    std::shared_ptr<Node> next;
    std::weak_ptr<Node>   prev; // Break cycle!
};

if (auto locked = w.lock()) {
    locked->doWork(); // Safely promoted
} else {
    // Object already destroyed!
}

Lambda Expressions & Essential STL Algorithms Functional

Lambda Syntax: [capture](parameters) mutable -> return_type { body }

  • [] No captures | [=] Capture all by value | [&] Capture all by reference
  • [x, &y] Explicit capture: x by value, y by ref
std::vector<int> v = {5, 2, 8, 1, 9};

// 1. std::sort with lambda comparator
std::sort(v.begin(), v.end(), [](int a, int b) { return a > b; });

// 2. std::find_if
auto it = std::find_if(v.begin(), v.end(), [](int n) { return n % 2 == 0; });

// 3. std::transform (map operation)
std::vector<int> sq(v.size());
std::transform(v.begin(), v.end(), sq.begin(), [](int x) { return x * x; });

// 4. std::accumulate (reduce / fold)
int sum = std::accumulate(v.begin(), v.end(), 0);

Modern Concurrency & Thread Synchronization

Thread Management & Data Race Prevention Threading
#include <thread>
#include <mutex>

std::mutex g_mtx;
int counter = 0;

void safeIncrement() {
    // RAII Lock: locks on init, unlocks automatically on exit
    std::lock_guard<std::mutex> lock(g_mtx);
    ++counter;
}

int main() {
    std::thread t1(safeIncrement);
    std::thread t2(safeIncrement);
    t1.join();  // Block until t1 finishes
    t2.join();
}
Atomics, Async & Thread Safety Checklist Lock-Free
  • std::atomic<T>: Lock-free primitive operations backed by hardware atomic CPU instructions (lock xadd, CMPXCHG).
  • std::async: Launches task asynchronously, returns a std::future<T> that blocks on .get().
  • Deadlock Prevention: Always acquire multiple mutexes in identical order across all threads, or use std::scoped_lock lock(mtx1, mtx2); (C++17 deadlock-free lock).
std::atomic<int> atomicCounter{0};
atomicCounter.fetch_add(1, std::memory_order_relaxed);

// Async task with future
auto fut = std::async(std::launch::async, []() { return 42; });
int result = fut.get(); // Retrieves value

Critical Pitfalls, Undefined Behavior & Quick Reference

Memory Pitfalls Critical
  • Dangling Pointer: Accessing memory after delete ptr;. Fix: Set ptr = nullptr; or use smart pointers.
  • Double Free: Calling delete twice on the same address. Causes heap corruption crash.
  • Memory Leak: Allocating via new without matching delete before losing scope.
  • Iterator Invalidation: Modifying a vector (push_back) while iterating through it may trigger reallocation, invalidating all existing iterators!
Undefined Behavior (UB) Danger
  • Dereferencing a null or uninitialized pointer (*nullptr).
  • Signed integer overflow (e.g. INT_MAX + 1 is UB in C++).
  • Out-of-bounds array indexing (arr[10] on size 5). Use v.at(i) for bounds checking.
  • Returning a pointer/reference to a local stack variable.
  • Data races (two concurrent threads accessing memory where at least one writes without synchronization).
Modern C++ Best Practice Rules Summary
  • Never use raw new / delete; wrap in std::unique_ptr.
  • Pass large read-only objects by const T&.
  • Mark single-argument constructors explicit to prevent implicit conversions.
  • Use nullptr, never NULL or 0.
  • Enable compiler warnings: -Wall -Wextra -Wpedantic -Werror.
  • Run Sanitizers: -fsanitize=address,undefined.
